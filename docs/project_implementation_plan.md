# Project Implementation Plan Based on Ubuntu Server and Jetson Orin Nano Super Hardware

## Project Implementation Plan

The project will be implemented as a fully offline voice-enabled PDF query system running on the NVIDIA Jetson Orin Nano Super Developer Kit with 8 GB memory. The system will use Ubuntu Server as the operating environment, installed through the Jetson-compatible JetPack software stack. Ubuntu Server is suitable for this project because it provides a lightweight, stable, and resource-efficient environment without unnecessary graphical components. This allows more system resources to be used for speech recognition, document processing, vector search, local language model execution, and text-to-speech generation.

The first stage of the project will focus on preparing the hardware and operating system. The NVIDIA Jetson Orin Nano Super Developer Kit will be used as the central processing unit of the system. A 256 GB NVMe SSD will be configured as the main local storage device. This storage will contain the Ubuntu Server operating system, project source code, uploaded PDF documents, extracted text, SQLite database, ChromaDB vector database, embeddings, logs, model files, and configuration files. Since all data will remain on the local device, the system will support the main privacy requirement of the project.

After installing Ubuntu Server, the basic system environment will be configured. This includes setting up Ethernet connectivity for installation and updates, installing Python, creating a virtual environment, installing required Python libraries, and configuring system services. Docker may also be installed for easier management of services and dependencies. Docker should be installed from Docker's official Ubuntu repository, as recommended by the official Docker documentation. Ollama can be installed on Linux using the official Linux installation method and used to run a local language model on the Jetson device.

The next stage will focus on audio input and output. The Jetson Nano USB Audio Codec sound card with two built-in microphones will be used to capture the user's voice. The microphone input will be tested in Ubuntu Server using audio tools to make sure that the system can correctly detect and record sound. External speakers will be connected for audio output. These speakers will be used to play the final spoken answer generated by the text-to-speech module.

After the audio hardware is configured, the speech-to-text module will be developed. Vosk will be used for offline speech recognition because it can convert voice into text locally without sending the user's voice to an online server. This module will receive audio from the microphone, process the spoken question, and convert it into written text. The main goal of this stage is to ensure that the system can understand user questions in a local and privacy-preserving way.

The document processing stage will prepare PDF documents for searching. The user-provided PDF files will be stored locally on the NVMe SSD. The system will extract text from these PDF files using tools such as PyMuPDF and LangChain document loaders. The extracted text will then be divided into smaller meaningful chunks. These chunks will be stored with metadata such as document name, page number, section number, and text ID. SQLite will be used to store structured metadata, while ChromaDB will be used to store vector embeddings for semantic search.

The retrieval stage will use semantic search to find the most relevant information from local documents. When the user asks a question, the question will be converted into an embedding and compared with the stored document embeddings in ChromaDB. The most relevant document chunks will be selected and passed to the local language model. This method will help the system answer based on the actual document content instead of guessing from general knowledge.

The answer generation stage will use a local language model through Ollama. The local model will receive the user's question and the retrieved document context, then generate a clear and relevant answer. Since the model runs locally on the Jetson device, the user's question and documents will not be sent to cloud-based artificial intelligence services. This supports the main goal of the project: offline operation and privacy protection.

After the answer is generated, a response validation step will be added. This step will check whether the answer is related to the retrieved document content and whether it avoids unnecessary or unsupported information. The purpose of this stage is to reduce incorrect answers and make the system more reliable for educational or institutional use.

The final response will be converted into speech using Piper. Piper will run locally on Ubuntu Server and will convert the generated text answer into a spoken response. The spoken answer will then be played through the external speakers. This completes the full interaction cycle: voice input, speech-to-text conversion, document search, answer generation, text-to-speech conversion, and speaker output.

The ESP32-S3 with two round screens will be used as the visual feedback module. These screens will work as robotic eyes and will show different states of the assistant, such as idle, listening, processing, speaking, and error. This module is not part of the core document retrieval process, but it improves the user experience and gives the project a more complete robotic appearance.

The deployed voice interaction is also designed for natural multi-turn use. After the wake word is detected, Adam gives a short spoken acknowledgment, listens for the first question, answers it, and then keeps a follow-up listening window open. This allows the user to continue the conversation without repeating the wake word every time. If no follow-up speech is detected before the timeout, the assistant returns to wake-word mode.

The answer-routing logic uses document retrieval only when the retrieved chunks are relevant to the question. If retrieved documents are weak or unrelated, the voice pipeline falls back to the same general virtual receptionist answer strategy used by the web Ask interface. For institution-specific questions that require official local knowledge and no matching document is available, the assistant asks the user to upload the missing brochure, policy, contact sheet, or source file instead of inventing details.

During local generation, Adam can give short spoken thinking feedback so the user knows the system is working. This feedback is stopped and interrupted before the final answer begins, preventing filler speech from overlapping with the answer.

The final stage will be system testing and evaluation. The system will be tested using different types of questions from local PDF documents, general voice questions, and multi-turn follow-up conversations. The main testing criteria will include speech recognition accuracy, document retrieval accuracy, answer relevance, response time, offline functionality, audio output quality, and overall usability. The results will be recorded and used in the Results and Discussion section of the thesis.

## Current Voice Interaction Behavior

The current systemd deployment runs Adam through adam.service and loads configuration from .env.example. The active voice behavior is:

- Wake word: adam, with aliases such as atom, add em, and add him for Vosk misrecognitions.
- Wake acknowledgment: enabled, using short phrases such as Yes? or I'm listening.
- Continuous conversation: enabled. Adam listens for follow-up questions for 45 seconds after each answer.
- STT protection: speech-start timeout and a small pre-speech buffer help avoid clipping the beginning of questions.
- General fallback: voice can answer general questions when document context is irrelevant, matching the web Ask behavior.
- Thinking feedback: brief filler phrases may play while generation is running, but filler audio is stopped before final answer playback.
- Logging: voice interactions are stored in SQLite voice_logs with transcript, answer, knowledge source, filler count, barge-in status, timing, and system resource fields.
